Cyan：训练故障诊断与受控修复

这是一条从用户启动训练，到进程失败、证据选择、Incident Agent 调查、人工批准、验证和原命令重跑的完整链路。页面先讲一条主线，再解释每个模块的所有权。

local daemon TCP loopback NDJSON + JSON-RPC 2.0 human approval evidence-gated proposal original exit code decides resolution

先看主链路：一次真实训练失败

用户只需要在 TUI 中预览并启动训练命令。训练过程由 daemon 持有；Agent 不负责启动训练，也不直接改工作区。

1 · User surface/monitor 输入命令，/start 确认启动
2 · JobSupervisor启动真实进程，持续排空 stdout/stderr 并写入 Attempt
3 · Incident非零退出创建 Failure Capsule 和 Incident run
4 · IncidentRuntime选择有限证据，输出诊断，并在证据充分时提出补丁
5 · Outcome合理停止于诊断，或经人工批准进入受控修复

一、从用户操作到真实训练进程

1

TUI 连接 Core

TUI 使用 SocketClient 连接 cyan-core。命令请求通过本机 TCP 发送，每行是一个 JSON-RPC 消息；事件则通过同一连接异步推送。

2

预览训练命令

launch.preview 解析用户输入，确定 argv、工作目录、环境覆盖项和 fingerprint。此时还没有启动训练进程。

3

确认并启动

launch.start 重新解析命令并检查 fingerprint 是否仍匹配。通过后由 CoreApp 调用 JobSupervisor.start()。

4

监督 Attempt

Supervisor 使用 asyncio.create_subprocess_exec 启动进程组，stdin 为 DEVNULL，stdout 和 stderr 分别持久化。Job 状态和 Attempt 状态也同步写入 JobStore。

TUI / VS Code
  -> SocketClient.send_command("launch.preview")
  -> SocketClient.send_command("launch.start")
  -> SocketServer._handle_line()
  -> CoreApp._launch_start_handler()
  -> CoreApp._start_job()
  -> JobSupervisor.start()
  -> JobSupervisor._launch()
  -> asyncio.create_subprocess_exec(...)

二、进程失败如何变成 Incident

Supervisor 是训练进程的唯一所有者。它不会把故障交给一个模糊的“后台 Agent”；它先把进程结果、日志和状态封口，再调用 Incident 领域。

日志先落盘

监控任务等待进程退出，同时持续读取 stdout/stderr。退出后写入 Attempt 的 return code、signal、结束时间和 failure.json。

失败回调

只有真实的 process_exit 故障会触发 CoreApp._job_failure_handler()，再进入 IncidentCoordinator.handle_failure()。

Failure Capsule

Coordinator 根据 Attempt 和不可变日志构造 Failure Capsule，并记录 cwd、命令、退出信息、日志范围和哈希。

创建本轮 Run

Incident、状态和 runs/<run_id>/run.json 在后台 Agent 任务开始前写入。随后 Coordinator 才启动 IncidentRuntime。

JobSupervisor._monitor()
  -> write Attempt / FailureRecord
  -> _notify_failure()
  -> CoreApp._job_failure_handler()
  -> IncidentCoordinator.handle_failure()
  -> build_failure_capsule()
  -> _start_run()
  -> IncidentRuntime.run()

三、IncidentRuntime：进入 Agent 之前做什么

IncidentRuntime 是训练领域和通用 Agent 内核之间的适配层。它决定 Agent 能看到哪些证据、能使用哪些工具，以及本轮运行如何被记录。

1. 验证证据没有变化

Runtime 重新计算 stdout/stderr 的 SHA-256。如果日志在 Failure Capsule 之后发生变化，本轮直接失败，不继续调查。

2. 选择初始证据

Evidence Selector v1 分块扫描不可变日志，按固定规则选择有限范围。它不调用 LLM、不读源码，也不改变工具权限。

3. 创建 Incident profile

Profile 把 Failure Capsule、已选择证据、当前指令和上一轮有限结果组合成 system prompt，并固定当前 causal-support-abstention-v1 诊断契约。

4. 注册六个工具

四个工具只读；两个工具只写 Incident artifact，不写用户 workspace。

read_filelist_dirsearch_textread_job_logsubmit_diagnosispropose_patch

本轮固定边界

最多 12 步；总输入最多 128 KiB；初始日志证据最多 32 KiB。上下文只包含当前 Incident 所需信息，不注入旧会话或全局记忆。

提案不是默认动作

Diagnosis 必须显式声明 causal_support 和 patch_recommended。只有 direct + true 才能调用 propose_patch；其余情况应在诊断后停止。

IncidentRuntime.run()
  -> verify immutable log hashes
  -> select_evidence()
  -> build_incident_profile()
  -> AgentRunner.run_and_capture(
         instruction,
         run_id,
         profile,
         run_path,
     )

四、AgentRunner 与 AgentLoop

AgentRunner 负责组装一次受限运行；AgentLoop 负责重复执行“模型调用 → 工具调用 → 观察结果”。它们不负责训练进程管理，也不直接推进 Incident 状态。

AgentRunner.run_and_capture()

创建本轮目录和本地 EventBus，启动 EventWriter，建立 ExecutionContext，注册 profile 中的工具，然后创建 provider 和 AgentLoop。

ExecutionContext

保存当前指令、assistant 消息、tool result、步骤数、状态和输入大小。工具结果在模型协议中使用 user 消息返回，但这不代表新的人工输入。

while context is running:
  publish StepStartedEvent
  check serialized input budget
  response = provider.chat(messages, tools, system_prompt)
  append assistant text and tool calls

  if response requests tools:
      invoke each registered tool
      append tool results to context

  if response.stop_reason == "end_turn":
      mark success
  elif max steps or an error is reached:
      mark failure

  publish StepFinishedEvent

直接因果证据，且可单文件修复

causal_support=direct、patch_recommended=true。Agent 可以继续生成一次精确唯一替换的 proposal，但仍不能应用它。

推断证据，或不适合当前修复边界

inferred、外部数据/环境问题、依赖变更、多文件修复或证据不足时，保留结构化 Diagnosis，不虚构路径，也不生成 proposal。

重要边界：Agent 不能运行 shell、修改训练 workspace 或自行批准补丁。Diagnosis 可以是有效产物；只有通过证据门控的 Proposal 才能进入人工审批。

五、事件如何从进程内运行到客户端

项目把“进程内事件”和“跨进程 IPC”分成两层。Agent 只发布到 EventBus；Service 再决定哪些摘要应该通过 TCP 推送给客户端。

客户端先通过 event.subscribe 注册 topics 和 scope。需要恢复历史时，订阅会先进入 pending：历史事件在同一 writer 的共享写锁内完成回放，随后 activate 才放行已经排队的实时事件，从而保证 history-before-live。TUI 还会按当前 Job/Run ID 忽略旧目标的迟到事件。

正常推送仍是 kind: "event" 的 NDJSON；客户端可用 job.get 读取权威快照。事件负责驱动界面，Incident 和 Job 文件负责恢复。

六、人工批准后的修复闭环

Agent 结束后，Coordinator 分别读取 Diagnosis 和 Proposal。Diagnosis 会被持久化；只有同时存在通过门控的 Proposal，Incident 才进入等待批准。没有 Proposal 的诊断当前收敛为 unresolved，用户仍可通过 /incident 发起新一轮调查。

diagnosing→awaiting_approval→applying→smoke_running→smoke_passed / smoke_skipped→retry_running→resolved
diagnosing→ diagnosis only →unresolved→ FOLLOW_UP →diagnosing
1

Review

客户端通过 incident.review 获取提案对应文件的前后文本。用户看到的是生成的单文件补丁，而不是 Agent 任意写入后的工作区。

2

Apply

用户批准后，PatchService 检查 proposal 哈希、目标文件哈希、Git workspace 根目录和 git apply --check，然后才应用补丁。非 Git workspace 可以诊断和审阅 diff，但不能一键应用。

3

Optional Smoke

如果 workspace 声明了 Smoke verifier，它会在原训练命令前运行。Smoke 失败时可以安全回滚；Smoke 成功或被跳过后才进入重跑。

4

Retry

重跑使用 JobStore 中保存的原始 argv、cwd 和环境。只有原训练命令最终返回 0，Incident 才能进入 resolved。

如果重跑仍然失败：Coordinator 会把新的 Attempt 绑定回同一个 Incident，清理旧的 Agent artifacts，并重新开始证据选择和诊断，而不是静默地把失败标记为成功。

模块边界：每一层只拥有自己的问题

service

daemon 生命周期、TCP、NDJSON、JSON-RPC 路由和客户端事件推送。

training.jobs

真实训练进程组、Attempt、stdout/stderr、重跑所需的 argv/cwd/env。

training.incidents

Failure Capsule、证据选择、状态机、审批、PatchService、Smoke 和恢复。

agent

LLM provider、上下文、工具注册、AgentLoop 和运行事件；不拥有 IPC 或训练业务。

完整训练输出只保留在 Attempt 日志中。Incident artifacts 保存状态、哈希、证据引用、诊断、提案和验证结果，不重复复制大段日志、补丁正文或模型上下文。

评测边界：运行时之外如何验证这条链路

benchmarks/ 与产品运行环境隔离，使用带上游来源和依赖锁的真实训练故障。它用于测量证据检索、诊断和完整 Incident 闭环，不会向产品 Runtime 注入 benchmark 专用能力。

15 + 315 个故障案例（6 dev、9 frozen test）和 3 个正常 Control。
40.74%formal-v1 frozen-test resolved rate；case bootstrap 95% CI 为 14.81%–66.67%。
62.96%proposal valid rate；同一报告中的 unsafe proposal rate 为 22.22%。
9 / 9正常产品路径成功且未误触发 Incident；正式报告记录的基础设施错误为 0。

无工具诊断基线的匿名评审包已完成 144/144 项双人盲审、分歧复测和第三人裁决。详细数字见 formal-v1 report 与 human review。

版本解释：formal-v1 是冻结历史结果，早于当前 causal-support-abstention-v1 prompt。新的 abstention gate 必须写入新的 run-set 重新测量，不能用旧报告证明当前门控已经改善 unsafe proposal。评测范围仍限于单机 CPU/MPS 上稳定的非零退出，不覆盖 CUDA/NCCL、OOM、挂死或静默收敛异常。
当前公开入口是 cyan TUI，以及用于启动和停止 daemon 的 cyan core start / cyan core stop。页面描述的是当前代码路径；benchmark 是外部验证层，不是 Runtime 功能，也不把 roadmap 或通用 Agent 能力当作现有能力。
