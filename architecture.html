cyan. — 架构总览

面向本地 ML 训练崩溃的 Incident Agent。核心是一套受控的 Agent Harness：daemon 只监管真实训练进程，进程非零退出后才唤醒受限的只读 Agent，基于日志与工作区证据给出诊断与可选补丁，补丁经用户批准、由 harness 校验并应用，最终以原训练命令的退出码为唯一验收标准。

Python 3.12 · asyncio TCP 127.0.0.1:7437 · NDJSON · JSON-RPC 2.0 Textual TUI + 薄 VS Code 客户端 核心行数：jobs 1018 / incidents 2765 / transport 730

01系统总览：双进程 + 单一状态源

cyan 是一个本地双进程系统：客户端通过 TCP loopback 与 daemon 通信，daemon 是唯一持有进程组与持久化状态的权威进程。

# 进程边界与传输
cyan / cyan-tui / cyan VS Code          # 客户端：CLI、Textual TUI、薄 VS Code 插件
    │  TCP loopback · NDJSON framing · JSON-RPC 2.0
cyan-core                                # daemon：单一状态源
    ├── JobSupervisor         真实进程组唯一所有者
    ├── JobStore             file-backed 任务/日志/事件持久化
    ├── IncidentCoordinator 故障诊断与修复编排（Agent Harness）
    ├── AgentRunner / AgentLoop / ToolRegistry  通用 Agent 运行时
    └── EventBus / SessionManager

传输层 core/transport/

TCP 127.0.0.1:7437，NDJSON 按行分帧。命令/事件是 Pydantic v2 模型、按 type 判别联合。ipc_broadcaster 为每个客户端提供有界队列，慢客户端不会阻塞进程日志落盘。

协议模型 core/bus/

commands.py / events.py / envelope.py 定义 JSON-RPC 信封与全部消息；由 scripts/gen_protocol_doc.py 生成 WIRE_PROTOCOL.md。

进程内事件 core/events/

极简 in-process EventBus + EventWriter（写 events.jsonl）。Incident 用 summary_only 模式，只落状态事件、省略逐 token 与完整工具输出。

03核心洞察：通用 Agent 运行时，受控的 Incident Profile

仓库里有一个通用 Agent 运行时（AgentRunner + AgentLoop + 工具注册表 + 权限/压缩/子代理/MCP）。Incident Harness 复用同一引擎，但通过一个 RunProfile 把它收敛成"受限事故调查员"——不另起炉灶，而是换一张受限的 profile。

通用运行时（普通聊天）

  • 工具：read_file / write_file / bash / list_dir / task_* / note_save / spawn_agent / MCP…
  • 加载全局 ~/.cyan/context.md 与项目 .cyan/context.md
  • 可启用上下文压缩、分层记忆、子代理、MCP

Incident Profile（只读事故调查）

  • 工具白名单 6 个只读工具（见 §05）
  • max_steps = 12（步数上限）
  • compact_threshold = 0.0（禁用压缩，profile 不可被压缩移除）
  • summary_only_events = True（不落逐 token）
  • include_context = False（不读全局/项目 context、session notes）
  • evidence_refs（本轮工具实际返回的证据引用登记表）
为什么这样设计：把"智能"留给 LLM，把"确定性"留给 harness。诊断/补丁的内容由模型产生，但 diff 的生成、四重校验、应用、回滚、验收全部由 harness 完成、不依赖模型输出质量。这是整个产品安全性的根基。

04Jobs 层：真实进程监督

4.1 JobSupervisor —— 进程组唯一所有者

  • 用 asyncio.create_subprocess_exec 启动，分离 stdout/stderr 各自 drain到磁盘日志；不用通用 120 秒 BashTool。
  • 被监督的训练进程为非交互（DEVNULL stdin）。
  • 精确持久化 argv / cwd / env 用于重跑；成为父进程但不主动限制 CPU/GPU。
  • 崩溃后可终止整棵进程组（session leader + process group leader 校验）。

4.2 JobStore —— 文件即真相

~/.cyan/jobs/<job_id>/
├── job.json              # 公开任务状态
├── events.jsonl          # 状态事件序列（seq 递增，可修复损坏尾部）
├── launch.json           # 私有启动信息，0600，永不通过 RPC 返回/暴露给 Agent
├── attempts/<attempt_id>/
│   ├── attempt.json      # 单次尝试状态
│   ├── stdout.log        # 原始 stdout（按 byte cursor 读取）
│   ├── stderr.log        # 原始 stderr
│   └── failure.json      # 失败快照 + FailureCapsule
└── incidents/<incident_id>/   # 见 §05.6

日志只写磁盘、不逐行进 EventBus；TUI 按 byte cursor 读取并续传，完整日志留在磁盘。daemon 重启时 recover_interrupted() 把遗留的 starting/running 任务封口为 interrupted。

05Incident Harness：故障驱动的诊断与修复闭环

5.1 一条故障的完整生命周期

真实非零退出 / 异常信号
   → FailureCapsule（封口日志快照 + Git + 启动信息）
   → 唤醒只读 Agent（先取证，再 submit_diagnosis，可选 propose_patch）
   → awaiting_approval（diagnosis + evidence + diff 一起展示）
   → 用户批准 → harness 校验并 git apply
   → 可选 smoke（用户声明式 verifier）
   → 原命令重跑，退出码 = 最终真值
   → resolved / 失败则复诊

5.2 FailureCapsule —— 一次性取证快照

进程失败后，harness 把这一刻钉死成一个不可变胶囊，Agent 只能基于它和当前工作区调查：

FailureCapsule(
    job_id / attempt_id / argv / cwd,
    failure_kind: launch_error | process_exit | supervisor_error,
    returncode / signal,  git_head,  dirty_paths[:200],
    environment: # 仅白名单前缀 CUDA_/NCCL_/TORCH_ 等，剔除密钥
    stdout: LogSnapshot(size, sha256, included_start/end, tail),
    stderr: LogSnapshot(...),
)

5.3 只读工具集（6 个）

工具类型说明
read_file只读读工作区文件（≤64KiB，纯文本），返回带 path@sha256#line 的证据引用
list_dir只读列目录
search_text只读工作区文本检索，返回证据引用
read_job_log只读按 byte 范围读当前 incident 的日志；全周期 256 KiB 证据预算
submit_diagnosis结构化提交诊断（category/summary/root_cause/evidence/confidence），evidence 必须引用已观察引用
propose_patch结构化单文件精确 SEARCH/REPLACE，harness 在内存生成 diff，绝不改工作区
硬边界：Incident session 不注册 write / bash / MCP / Skill / TaskManager / subagent 工具，不加载全局/项目 context 与 session notes，不允许手动压缩覆盖 profile。

5.4 状态机 —— 单一事实源 incidents/fsm.py

状态流转由一张声明式转移表表达；运行时校验、mermaid 文档、单元测试都从同一张表派生。调用方只发事件（_dispatch(event)），机器算出目标状态；非法转移抛 IllegalTransitionError。

5.5 受控补丁链路 —— harness 拥有确定性

约束：模型只输出一个已有 UTF-8 文本文件（≤1 MiB）里的一次精确唯一 SEARCH/REPLACE，不写 diff 头/hunk/行号、不创建/删除/重命名/模糊匹配。

  1. 证据校验：proposal 必须引用本轮工具实际返回的 path@sha256#line，且 SEARCH 文本与当前文件唯一匹配（最多允许一次校正反馈）。
  2. harness 生成 diff：在内存做唯一替换 → 生成 UnifiedDiff → 只写为私有 artifact（proposal.diff）。批准前工作区零写入。
  3. 四重校验：路径解析（限制在 workspace 内）、文件 SHA-256、Git base / submodule 边界、git apply --check。
  4. 批准后应用：git apply → 写 apply.json（应用后文件哈希凭据）。
  5. 安全回滚：smoke/重跑失败时，仅在目标文件哈希仍等于 apply 后哈希时才反向应用；否则 rollback_blocked。

5.6 审批、smoke 与最终验收

  • 审批：awaiting_approval 时展示 diagnosis + evidence + diff，用户 approve / reject。批准前会核对 smoke 配置指纹，漂移则 stale。
  • smoke（可选，用户声明）：项目 .cyan/config.toml 的 [incident.smoke] 声明 argv + timeout；Agent 不能生成或修改它。失败则回滚并让同一只读 session 复诊。
  • 最终验收 = 原命令退出码：重跑精确原 argv/cwd/env，退出码 0 才算 resolved。smoke 只是廉价代理，不是真值。

5.7 Incident 制品布局

incidents/<incident_id>/
├── incident.json          # 状态 + active_run/proposal 指针
├── diagnosis.json         # 结构化诊断（含 evidence）
├── proposal.json          # 补丁元数据（patch_sha256 + 文件清单）
├── proposal.diff          # harness 生成的 unified diff
├── apply.json             # 应用后文件哈希凭据（回滚依据）
├── smoke.json             # smoke verifier 结果
├── smoke-execution.json   # smoke 子进程身份（PID + lstart）
└── evidence_usage.json    # 日志证据预算用量

06安全不变量一览

不变量机制
批准前工作区零写入diff 只落私有 artifact；propose_patch 从不改工作区
Agent 无 shell / 无写文件能力Incident profile 只注册 6 个只读/结构化工具
证据不可伪造evidence 引用必须命中本轮工具返回的登记表；日志引用按 byte 范围校验
补丁不可漂移路径 / SHA-256 / Git base / submodule / git apply --check 四重校验
回滚可审计apply.json 记录应用后哈希，仅哈希未变才反向应用
私密信息不外泄launch.json 0600、不返回 RPC、不暴露给 Agent；环境变量按白名单脱敏
慢客户端不阻塞IPC 每客户端有界队列；日志走 byte cursor 不逐行广播
崩溃可恢复状态机 recover_action + 文件持久化；smoke 进程终止前校验 PID/身份/session/pgroup

07关键设计取舍

读多不写 + 人工审批

牺牲自动化率，换取全程可审计与零误写。宁可用一道批准门槛降低吞吐，也不让模型直接改工作区。

模型给智能，harness 给确定性

diff 生成、校验、回滚、验收全部是确定性代码；模型只负责"改哪一行"。诊断准确率来自 LLM，安全边界来自 harness。

退出码 = 客观真值

用原训练命令退出码做唯一验收，形成可自动判定的闭环。9 例真实 LLM 验证：诊断 9/9，6 个代码故障首次批准后全部修复，3 个非代码故障零冗余补丁。

单文件单处替换

刻意不做多文件/多 hunk 补丁。范围越窄，校验越强、回滚越简单。这是产品边界，不是能力缺失。
